### 1.1 DB 데이터 정리 (Supabase에서 SQL 직접 실행)

`profiles` 테이블의 분류 필드 중복/혼재를 정리:

| 필드 | 변경 전 | 변경 후 |
|------|---------|---------|
| `contract_type` (NOT NULL) | NOT NULL 제약 | nullable로 변경 |
| `contract_type` (값) | 모두 'freelancer'로 채워져 있어 무의미 | admin 제외 전부 NULL |
| `role` ↔ `employee_type` | 일부 불일치 | 1:1 동기화 (admin/editor/employee → internal, freelancer → freelancer) |
| `mentor_role` | 빈 문자열/이상값 혼재 | 사수/부사수/NULL만 허용 |

**실행한 SQL (요약):**

```sql
-- contract_type NOT NULL 제약 해제
ALTER TABLE profiles ALTER COLUMN contract_type DROP NOT NULL;

-- role ↔ employee_type 동기화
UPDATE profiles SET employee_type = 'internal'
  WHERE role IN ('admin', 'editor', 'employee')
    AND employee_type IS DISTINCT FROM 'internal'
    AND name != 'admin';

UPDATE profiles SET employee_type = 'freelancer'
  WHERE role = 'freelancer'
    AND employee_type IS DISTINCT FROM 'freelancer';

-- contract_type 전체 비우기
UPDATE profiles SET contract_type = NULL WHERE name != 'admin';

-- mentor_role 정규화
UPDATE profiles SET mentor_role = NULL
  WHERE mentor_role IS NOT NULL AND mentor_role NOT IN ('사수', '부사수');
```

**현재 분류 체계 (확정):**

| 축 | 필드 | 가능한 값 |
|------|------|---------|
| 근무형태 | `role` | admin / editor / employee / freelancer |
| 직책 (조직 위치) | `position` | 대표 / 이사 / 총괄팀장 / 팀장 / 팀원 / null |
| 작업 역할 | `mentor_role` | 사수 / 부사수 / null |
| 팀 소속 | `team_id` | teams.id |
| 정산 분류 | `contract_type` | NULL (UI 숨김, 향후 정산 모듈에서 활용) |
| ~~고용 유형~~ | ~~`employee_type`~~ | role과 1:1 동기화로 중복 (폐기 검토 필요) |

### 🔴 [우선 1] Supabase RLS 정책 설정 (근본 보안 해결)

**왜 필요한가:**
이번 세션에서 UI/API 레벨로 차단했지만, 클라이언트가 supabase JS 직접 호출하면 우회 가능. 예: 프리랜서가 브라우저 콘솔에서 `supabase.from('assignments').select('*')` 호출하면 전체 배정 데이터가 그대로 옴.

**근본 해결:** Supabase RLS(Row Level Security) 정책을 테이블에 적용해서 DB 레벨에서 차단.

**대상 테이블별 정책 초안:**

| 테이블 | SELECT 정책 |
|--------|-----------|
| `profiles` | 본인 + 같은 team_id + admin/editor 만 |
| `branches` | 모든 인증 사용자 OK (담당자 정보는 API에서 차등화 유지) |
| `assignments` | 본인이 main/sub/optimal/inbl_writer_id인 행 + admin/editor/employee 전체 |
| `assignment_logs` | admin/editor 만 |
| `teams` | 모든 인증 사용자 OK |
| `partners` | admin/editor 만 |
| `notices` | 모든 인증 사용자 OK |

**작업 순서:**
1. 각 테이블의 현재 RLS 상태 확인
2. 정책 SQL 작성 (auth.uid() 활용)
3. 테스트: 프리랜서 계정으로 supabase 직접 호출 시 차단되는지
4. 기존 API의 service_role 사용 부분이 영향받는지 확인 (대부분 `createServerSupabase()`로 service key 사용 중이라 RLS 우회됨 — 정상 동작)
